# AI 실무 과제 Toolkit v3.0 — 공개 가능한 범용 작업 가이드

> **목적:** 새로운 데이터·업무·개발 과제를 만났을 때, 요구사항 파악 → 문제 정의 → EDA → 설계 → 구현 → 실행 → 독립 검증 → 문서화의 품질을 높이는 **작업 절차 및 프롬프트 모음**.
>
> 이 저장소에는 실제 과제 지문, 특정 시험 복기, 조직 내부 자료, 개인정보, 정답 코드, 접근 정보가 **들어 있지 않습니다**. 범용 문서·빈 템플릿·일반 CSV 점검 스크립트만 제공합니다.
>
> **공식 지시·허용 도구·제출 형식 > 실제 과제 README·기존 코드 > 이 Toolkit의 예시.** 허용 여부가 불확실하면 외부 도구를 사용하거나 정보를 전송하지 마세요.

## 30초 사용법

1. **과제 프로젝트의 폴더**를 먼저 확인합니다. Toolkit은 별도 폴더에 둡니다.
2. `QUICK_START.md`를 열고 `PROMPTS.md`의 **Bash 1 역할 프롬프트**를 Codex 대화창에 처음 한 번 입력합니다. `AGENTS.md`를 **명시적으로 읽게 합니다**. 자동 적용을 가정하지 않습니다.
3. `PROMPTS.md`에서 **현재 단계의 프롬프트만** 사용합니다. 공식 요구사항과 프로젝트 경로를 실제 값으로 확인시킵니다.
4. 가능하다면 Bash 2를 독립 검증 전담으로 둡니다. **별도 문서화 세션은 사용하지 않습니다.** 마지막 문서화는 Bash 1이 담당합니다.
5. CSV 점검 스크립트는 **선택 사항**입니다. Python 스크립트 없이도 Codex가 코드를 실행해 EDA하고 결과를 `outputs/EDA_REPORT.md`에 정리할 수 있습니다.

## 파일 구조 (13개 파일, 하위 폴더 2개)

```text
ai-hackathon-toolkit/
├── README.md                  이 문서: 사용 순서·역할·FAQ·공개 보안
├── AGENTS.md                  AI 공통 원칙·P0/P1/P2·파일 수정 권한
├── QUICK_START.md             초기 점검, 실제 프로젝트/Toolkit 분리
├── PROMPTS.md                 Bash 1/2 초기화 + 8단계 복사 프롬프트 + 문서화
├── ALGORITHM_GUIDE.md         EDA/설계/구현 구별, 시스템·알고리즘·사용자 역할
├── VALIDATION_GUIDE.md        독립 QA, 데이터/제약/UI 검증, 이슈 보고
├── COMMAND_CHEATSHEET.md     셸 명령, Git, Python, 서버/포트/Browser Preview
├── templates/
│   ├── TASK_PLAN.md           요구 ID, 필수도/우선순위, 결정·진행 근거
│   ├── REVIEW_REPORT.md       Bash 2 테스트·결함·재검증 기록
│   └── HANDOFF.md             검증된 실행/사용/제출 문서 초안
├── scripts/
│   └── profile_csv.py         선택적, 읽기 전용 CSV 기본 점검 도구
├── .gitignore                 Toolkit 저장소의 임시 파일 등 제외
└── LICENSE                    Toolkit 자체 MIT 라이선스
```

이 저장소의 템플릿은 **제출물이 아니라 양식**입니다. 실제 과제 프로젝트에서 작성할 때만 필요한 파일을 복사/생성합니다. 공식 파일명과 위치가 지정되어 있다면 그쪽을 우선합니다.

## 과제별 작업 흐름·도구·기대 결과

| 단계 | 담당 | 무엇을 하는가 | 과제 프로젝트 안의 산출물(기본 제안) |
|---|---|---|---|
| 1. README·환경·제출 파악 | Bash 1 | 필수 요구·성공 기준·기존 코드·실행법·제출 조건 확인 | `outputs/TASK_PLAN.md` 초안 또는 응답 |
| 2. 업무 문제 정의 | Bash 1 + 허용된 업무 담당자/AI | Hard/Soft/Objective/가정, 미확정 규칙 질문 | `outputs/TASK_PLAN.md` 결정·질문 섹션 |
| 3. EDA·품질 확인 | Bash 1; Bash 2 일부 재확인 | 실제 입력을 읽어 구조/결측/중복/키/범위 확인 | `outputs/EDA_REPORT.md`; 선택 시 `outputs/data_profile.json` |
| 4. 시스템 설계·알고리즘 선택 | Bash 1 | 데이터 흐름, 입력/출력 계약, 기준선, 알고리즘 선택 이유 | `outputs/TASK_PLAN.md` 설계·trade-off 섹션 |
| 5. 핵심 기능 구현·계산 | Bash 1 | 최소 입력→계산→결과(P0)를 실제 실행 | 요구된 소스·결과 데이터·기본 기능 |
| 6. 실행·브라우저 확인 | Bash 1 + 사용자 | 실제 실행 명령·포트·API·UI/다운로드 확인 | 실행 로그·실제 화면/응답·수정 코드 |
| 7. 독립 QA·재검증 | Bash 2 → Bash 1 → Bash 2 | 원본과 결과의 독립 계산, 결함 수정·재검증 | `outputs/REVIEW_REPORT.md` |
| 8. 최종 문서화·제출 점검 | Bash 1 (Scribe 모드) | README/코드/Bash 2 보고를 대조 | 요구 시 `HOW_TO_RUN.md` 등 **공식 지정** 산출물 |

**문서 저장 안전장치:** `outputs/`가 공식 제출물만 모으는 전용 폴더이거나 자동 수집 대상이라면, 내부 메모(`TASK_PLAN.md`, `EDA_REPORT.md`, `REVIEW_REPORT.md`)를 거기에 넣지 마세요. 대신 공식 규칙이 허용하는 별도 비제출 폴더(예: `work_notes/`)를 정해 **처음부터 두 세션에 같은 경로를 전달**하세요. 기존 파일 덮어쓰기 금지.

이것은 **기본 진행 순서**입니다. 단계 2의 질문은 3~5단계에서 반복할 수 있고, **독립 QA는 3단계부터 병행**할 수 있습니다. 웹 UI가 요구되지 않으면 6단계의 브라우저 확인은 생략합니다. 실제 제출 절차는 공식 규정에 맞춥니다.

### 공통 우선순위: P0/P1/P2

- **P0:** 공식 필수 요구사항 및 핵심 동작·주요 제약·필수 실행/제출 조건. 무엇이 P0인지 README 기준으로 결정.
- **P1:** 공식 필수가 아닌 오류처리·안정성·사용성 개선. 공식 필수인 오류처리·문서는 **P0**입니다.
- **P2:** 공식 필수가 아닌 고급 최적화·시각화·외부 연동. 공식 필수인 최적화·시각화는 **P0**입니다.

`Must/Should/Could`는 **요구의 필수 여부**, `P0/P1/P2`는 **실행 우선순위**입니다. 서로 다른 축이며, 공식 필수 사항을 편의대로 낮추지 않습니다.

## Bash 1 / Bash 2 — 세션별 소유권

| 역할 | 주요 책임 | 수정 가능한 대상 | 수정하면 안 되는 대상 |
|---|---|---|---|
| **Bash 1 — Main Developer / Tech Lead** | 분석, 계획, 설계, 기능 구현, 실행, 최종 Scribe 문서화 | 과제 소스 및 `outputs/TASK_PLAN.md`, `outputs/EDA_REPORT.md`, 공식 실행 문서 | 원본 데이터(승인 없는 직접 수정), Bash 2의 `outputs/REVIEW_REPORT.md` |
| **Bash 2 — Independent Reviewer / Senior QA** | 원본·공식 요구·최종 결과 독립 검증 및 재검증 | `outputs/REVIEW_REPORT.md`, 별도 승인된 QA 테스트 파일 | 앱 소스, 원본 입력, Bash 1 문서 |

- 세션 간 **대화 내용은 자동 공유되지 않습니다**. 둘 다 실제로 같은 과제 폴더를 보고 있는지 `pwd`와 공유 테스트로 확인합니다.
- 역할 프롬프트를 입력하면 **초기 조사/검증 계획**이 나오지 완성된 앱이 저절로 생성되지는 않습니다. 단계별 작업 지시를 이어서 줘야 합니다.
- 두 세션 분리가 불가능하면 Bash 1만 사용하되 **별도 검증 절차**를 수행합니다. Bash 2가 있다고 자동으로 독립성이 확보되는 것도 아닙니다. 검사 방법과 입력 근거를 분리해야 합니다.

## GitHub 공개 저장소 사용과 최신 내용 반영

**업로드 전:** ZIP을 풀어 파일을 검토하고 자신이 소유한 GitHub Public 저장소에 업로드합니다. 공개 여부·외부 도구 사용은 해당 환경 규정으로 먼저 확인합니다.

```bash
# 실제 과제의 작업 폴더가 아닌, 허용된 별도 위치에서 (경로/URL은 예시)
git clone <PUBLIC_REPOSITORY_URL> ai-hackathon-toolkit
```

- GitHub 웹에서 `.md` 수정 → **Commit changes** 하면 새로운 `git clone`은 수정된 최신 커밋을 가져옵니다.
- 이미 clone했다면, **Toolkit 폴더에 로컬 변경이 없을 때** `git -C ai-hackathon-toolkit pull --ff-only`로 갱신합니다. 로컬 변경이 있으면 충돌 처리가 먼저입니다.
- Toolkit 폴더를 과제 프로젝트와 혼동하거나 Toolkit 전체를 과제 제출물에 그대로 포함하지 않습니다.
- GitHub Public 저장소에는 **진행 중인 과제의 README·입력/결과 데이터·스크린샷·대화 내용·API 키·업무 담당자의 답변을 업로드하지 않습니다**. `outputs/`도 과제 저장소의 산출물이므로 공개 게시 금지 여부를 별도 확인해야 합니다. Toolkit의 `.gitignore`가 다른 저장소를 자동 보호하지는 않습니다. **커밋 직전에 `git status --short`와 `git diff --cached --name-only`로 공개 대상 파일을 직접 확인**합니다. 무심코 업로드한 자료는 나중에 삭제해도 Git 이력이나 복제본에 남을 수 있습니다.

## 자주 헷갈리는 개념

**Q. `.md`와 `.py`는 어떻게 다른가?** `.md`는 Codex가 읽을 자연어 지침·빈 양식입니다. `.py`는 셸에서 **실행하는 선택적 코드**입니다. CSV가 아니라면 `profile_csv.py`를 사용할 이유가 없습니다.

**Q. 스크립트 없이 EDA하면 어디에 저장되는가?** 저장 지시가 없으면 채팅 응답으로 끝날 수 있습니다. `PROMPTS.md` 3단계는 Codex가 확인/실행한 결과를 **과제 폴더의 `outputs/EDA_REPORT.md`**에 저장하게 합니다. Python·SQL 등 필요한 코드 실행은 Codex가 상황에 맞게 합니다. `outputs/data_profile.json`은 **`profile_csv.py` 실행 시에만 생기는 선택적 파일**입니다.

**Q. 운영자와 개발자용은 무엇이 다른가?** 운영자는 데이터 입력·설정·실행·결과 관리 등의 **업무 화면/기능**을 의미할 수 있습니다. 개발자는 코드·로그·테스트·배포를 담당하는 **구현/유지보수 역할**이며 별도 웹 화면이 필수는 아닙니다. 조회 전용 사용자가 필요한지도 요구사항으로 판단합니다. 로그인·권한·관리자 화면은 요구될 때만 구현합니다.

**Q. 3000/8000 포트가 필수인가?** 아닙니다. 둘 다 흔한 예시 포트입니다. 실제 `package.json`, 설정, 서버 로그에서 확인해야 합니다. `http://localhost:3000`은 **현재 접근하는 환경의 3000 포트**를 뜻하며, 클라우드 IDE의 Browser Preview가 연결하는 주소는 플랫폼별로 다를 수 있습니다. `COMMAND_CHEATSHEET.md` 참고.

**Q. 7요소 프롬프트 템플릿/Few-shot이 항상 필요한가?** 아닙니다. 최초 역할 프롬프트가 페르소나·기본 목표·공통 제약을, 과제 README가 컨텍스트를, 단계별 프롬프트가 작업·산출물 형식을 담당합니다. Few-shot은 출력 예가 정말 필요할 때만 추가합니다.

**Q. 왜 설계가 EDA 다음이고 계산·최적화 구현 전인가?** EDA로 입력과 문제를 파악한 뒤, 설계에서 입력→계산→출력 흐름·모듈 역할·제약·알고리즘을 결정해야 뒤늦은 구조 변경을 줄일 수 있기 때문입니다. 설계는 짧게 하고 **실행 가능한 P0를 조기에 완성**합니다.

**Q. 별도 문서 작성 세션 없이 누가 문서를 만드는가?** 마지막에 Bash 1에게 `PROMPTS.md` 8단계 **Scribe 모드**를 요청합니다. 이때 Bash 2 검증 보고서를 직접 읽어야 하며 소스·원본은 수정하지 않습니다.

## 보안·정확성 원칙

1. 비공개 문제·실제 데이터·개인정보·직원/고객 정보·토큰·내부 대화·스크린샷을 공개 GitHub나 허가되지 않은 도구로 보내지 않습니다. 공개 저장소와 **과제 작업 공간은 엄격히 분리**합니다.
2. 외부 공개 코드·MCP·플러그인·라이브러리·AI 도구는 **현재 과제 규정이 허용한 경우에만** 사용합니다. 라이선스와 출처를 준수하며 완성된 외부 솔루션으로 과제 전체를 대체하지 않습니다.
3. Codex가 "완료"라고 해도 파일·실행 명령·로그·독립 검증이 없는 항목은 검증 완료가 아닙니다.
4. 미검증·가정·불가능·미구현은 명확히 표시합니다. 데이터 수정·예외 레코드 제외·강제 조건 완화는 승인 없이 하지 않습니다.
5. 이 Toolkit은 **공개 가능한 일반적인 작업 방법론**으로 구성했지만, 개별 환경의 반입/사용·제출 허용 여부를 보장하지 않습니다.
